# WEBAGENT.KR — 개발자용 통합 MVP 기획서

## 0. 절대 원칙 (변경 불가)

1. "홈페이지 제작"을 서비스 전면에 노출하지 않는다. 홈페이지는 `Smart Website` 서비스의 하위 결과물로만 취급한다.
2. 서비스는 `AI Automation / n8n Automation / Smart Website / AI Agent / AI Consulting` 5종을 유지한다. 재분류·통합 논의로 되돌아가지 않는다.
3. 실제 고객 사례가 없는 데모는 반드시 `자동화 데모` 또는 `샘플 구축 사례`로 표시한다.
4. AI 분석 결과의 예상 효과(절감 시간 등)는 추정치임을 항상 명시한다.
5. 기술 스택은 `Next.js + TypeScript + Supabase + n8n + Telegram`으로 고정한다.

---

## 1. 제품 정의와 포지셔닝

> 중소기업 사용자가 반복 업무를 입력하면 AI가 자동화 가능성을 분석하고, 맞춤 결과를 보여준 뒤 상담으로 연결하는 AI 자동화 영업 플랫폼

- 브랜드: `WEBAGENT.KR`
- 슬로건: **AI로 일하는 회사를 만듭니다.**
- 포지셔닝: 일반 웹에이전시(홈페이지·쇼핑몰·앱 제작)가 아니라 **AI 자동화 구축 전문기업**. 이렇게 정의해야 가격 경쟁 구도에서 빠져나올 수 있다.

핵심 검증 가설: *중소기업 대표자·실무자는 단순 "문의하기"보다 자기 회사 업무를 분석해 주는 "무료 자동화 진단"에 더 적극적으로 반응한다.*

전환 흐름(이 흐름 하나를 완성하는 것이 MVP의 유일한 목표):

```
사이트 방문 → 서비스 이해 → 무료 자동화 진단 → AI 분석 결과 → 상담 신청 → 제안·계약
```

> [의견] 페이지 수를 늘리는 방향의 논의는 전부 후순위다. 이 한 줄짜리 흐름이 깨지지 않고 끝까지 이어지는지가 유일한 채점 기준이어야 한다. 개발 중 우선순위 판단이 애매할 때는 "이게 이 흐름을 완성하는 데 필요한가"로 되돌아가서 판단한다.

## 2. 타깃 고객

**1차 타깃**: 직원 5~50명, 내부 개발자 없음, Excel/이메일/문서 업무 비중 높음, 홈페이지 문의·고객정보를 수동 관리, AI 도입 의지는 있으나 시작점을 모르는 대표자.

**초기 집중 업종** (우선순위 순): ① 건설·인테리어·부동산 ② 전문서비스업 ③ 교육·학원·컨설팅 ④ 제조·유통업 ⑤ 1인 기업.

건설·인테리어·부동산을 1순위로 두는 이유는 시장 크기가 아니라 대표자 보유 네트워크 때문이다(3장 트래픽 전략 참고). 초기 데모·사례는 이 업종을 우선 제작한다. 실제 고객 구축물이 아니면 반드시 `자동화 데모` 또는 `샘플 구축 사례`로 표기한다.

## 3. 사업 현실성 체크리스트

> [의견] 이 절 전체가 기존 3개 문서에 없던 내용이다. 제품·트래픽·과금·일정은 이미 상세히 짜여 있는데, 그 아래 깔려야 할 "사업을 실제로 운영하기 위한 최소 행정·재무 준비"가 비어 있다. 개발을 시작하기 전에 아래를 확인해야 뒤에서 막히지 않는다.

| 항목 | 확인 필요 사항 | 비고 |
|---|---|---|
| 사업자등록 | 개인/법인 사업자등록 여부 | 계약금·중도금을 받으려면 세금계산서 또는 현금영수증 발행 주체가 있어야 함. 없다면 첫 계약 전까지 등록 필요 |
| 결제 수단 | 초기엔 계좌이체로 충분 | 카드결제·전자세금계산서 자동 발행은 P2. 초기엔 수기 세금계산서로 처리 |
| AI API 비용 | 진단 1건당 예상 토큰 사용량 산정 | 아래 15.3절 참고 — 서비스 구조상 원가는 매우 낮으나 예산에 명시적으로 잡아둘 것 |
| 서버·도메인 비용 | Contabo VPS + 도메인 | 월 서버비 약 1.5~3만원 + 도메인 연 2만원 내외로 예산에 반영 |
| 배상·책임 조항 | 견적서/계약서에 하자보수 범위 명시 | 2.5절(견적서 표준 구조)의 "무상 보증 기간" 조항으로 대응 |

이 표의 항목 중 아직 확인되지 않은 것은 1주차 작업 시작 전에 사용자님이 직접 확인해야 하는 전제조건이다(개발 착수를 막지는 않지만, 첫 계약 성사 시점 전까지는 반드시 해결되어야 함).

## 4. MVP 범위

### P0 — 출시 필수

- 반응형 랜딩페이지
- 5단계 무료 AI 자동화 진단 폼 (7.4절: 스팸 방어 포함)
- 고객·진단 원본 DB 저장
- n8n Webhook + AI 분석 (Mock 데이터 우선 전략, 9.4절)
- 구조화된 분석 결과 저장·조회
- 처리중/완료/실패 상태를 갖는 결과 페이지
- Telegram 관리자 알림 (신규 진단 + **시스템 에러 알림**, 16.4절)
- 상담 신청 + DB 저장 + 서비스 유형 자동 태깅(11.3절)
- 개인정보 수집 동의 + 개인정보처리방침(**국외이전 고지 포함**, 16.1절)
- 관리자 로그인, 진단·상담 목록/상세 조회
- **GA4 5단계 이탈 이벤트**(14.4절) — 새 기능이 아니라 기존 폼에 이벤트 태그만 추가하는 작업이므로 P0에 포함해도 일정 영향 거의 없음
- Docker 기반 배포 + DB 백업

> [의견] 원안(01, webagent_기획안)에는 P1이었던 GA4 이벤트 설계를 P0로 올렸다. 방문자 수가 적은 초기 몇 주에는 "왜 이탈했는지"를 아는 것 자체가 KPI 재설정의 유일한 근거가 된다. 나중에 붙이면 그 몇 주치 데이터는 영영 못 얻는다.

홈 화면 섹션 순서: `Hero → 문제 제시 → Before/After → 서비스 5종 → 사례 → 진단 CTA → 구축 절차 → 신뢰 요소 → FAQ → 최종 CTA`

서비스 5종은 MVP에서 개별 상세 페이지 없이 홈의 카드형 섹션으로만 노출한다.

**Hero**
- 헤드라인: `AI가 직원처럼 일하는 회사` / 슬로건 통일 문구: `AI로 일하는 회사를 만듭니다.`
- 설명: 고객 문의, 견적, 보고서, 콘텐츠 제작까지 반복 업무를 AI와 n8n으로 연결하고 자동화합니다.
- CTA: `무료 자동화 진단` / `자동화 사례 보기`
- 시각 요소: AI 로봇 이미지 대신 실제 흐름 `문의 → AI 분류 → DB 저장 → 담당자 알림 → 답변 초안`

**문제 제시**: "아직도 이런 업무를 사람이 반복하고 있나요?" — 문의 수동 확인, 엑셀 재입력, 견적서 매번 재작성, 상담 수기 정리, 블로그·SNS 직접 제작, 보고서 복사·작성.

**Before/After 비교표**

| 업무 | 기존 방식 | 자동화 후 |
|---|---|---|
| 고객 문의 | 이메일 수동 확인 | 접수 즉시 저장·알림 |
| 고객 관리 | 엑셀 수기 입력 | CRM 자동 등록 |
| 견적 작성 | 양식 복사·수정 | AI 초안 생성 |
| 상담 정리 | 직원 수기 작성 | AI 자동 요약 |
| 블로그 | 조사부터 직접 수행 | 자료·초안 자동 생성 |
| 보고서 | 자료 복사 후 작성 | 지정 양식 자동 생성 |

**서비스 5종**: AI Automation(반복 사무·영업·관리 업무 자동화) / n8n Automation(API·이메일·DB·메신저·AI 모델 연결) / Smart Website(문의 접수·고객관리 연결 자동화 홈페이지) / AI Agent(사내 문서 검색·고객 상담·자료 생성) / AI Consulting(AI 도입 진단·실무 교육·운영 컨설팅).

**대표 자동화 데모 3개** (전부 `자동화 데모` 라벨 필수)

1. **문의 자동화**: 문의 제출 → AI 유형 분류 → DB 저장 → 담당자 알림 → 접수 이메일 → 답변 초안. 효과: 문의 누락 방지, 응답 속도 개선, 고객 데이터 축적.
2. **견적 자동화**: 견적 요청 → 요구사항 분석 → 추가 질문 → 견적 초안 → 관리자 검토. 효과: 작성 시간 단축, 상담 기준 표준화.
3. **콘텐츠 자동화**: 키워드 → 자료 수집 → AI 초안 → 이미지 준비 → WordPress 임시글 → 사람 검수(반자동, 완전 자동 발행 아님). 효과: 신뢰도·품질 유지.

## 6. 핵심 사용자 여정

1. 방문자가 문제 제시·Before/After·사례를 확인한다.
2. 무료 진단을 시작해 회사·업무·연락 정보를 단계별로 입력한다.
3. 제출 직후 공개 식별자가 포함된 결과 페이지로 이동한다.
4. 처리중 상태를 안내하고, 완료되면 구조화된 결과를 표시한다.
5. 결과 하단에서 상담 신청 / 결과 이메일 수신 / 다시 진단하기 중 선택한다.
6. 관리자는 Telegram 알림을 받고 관리자 화면에서 상태를 관리한다.

## 7. 진단 폼 상세 스펙

| 단계 | 내용 |
|---|---|
| 1. 회사 정보 | 회사명, 업종, 직원 수, 홈페이지 유무 |
| 2. 사용 도구(복수 선택) | Excel, Google Sheets, 이메일, 카카오톡, ERP, CRM, WordPress, 네이버, Slack, Telegram, 기타 |
| 3. 반복 업무(복수 선택) | 문의, 견적, 고객정보, 이메일, 보고서, 블로그, SNS, 문서 정리, 상담 기록, 내부 알림 |
| 4. 업무량·문제 | 하루 반복 시간, 담당 인원, 월 처리량, 가장 불편한 업무, 현재 처리 방식 |
| 5. 상담 정보 | 도입 목적, 예산 범위, 상담 방식, 이름, 이메일, 전화번호, 개인정보 동의 |

**UX 규칙**: 한 화면에 모든 문항을 노출하지 않는다. 각 단계에 진행률·이전/다음 버튼·명확한 오류 메시지를 제공한다. 최종 제출은 한 번만 실행되도록 제출 버튼 비활성화 처리(중복 제출 방지)를 반드시 구현한다.

### 7.4 스팸·어뷰징 방어 (P0, 신규)

> [의견] 무료 진단은 별도 로그인 없이 누구나 제출 가능한 공개 폼이다. 경쟁사 스크래핑, 봇, 장난성 제출에 노출될 수 있는데 기존 3개 문서 어디에도 방어 설계가 없다. 아래는 개발 리소스가 거의 들지 않는 최소 방어선이다.

- **허니팟 필드**: 화면에는 보이지 않는 hidden input을 폼에 추가하고, 값이 채워져 제출되면 봇으로 간주해 서버에서 조용히 무시(200 응답은 정상 반환해 봇에게 신호를 주지 않음).
- **Rate limit**: 동일 IP 기준 시간당 진단 제출 5건 제한 (Next.js API Route 또는 n8n Webhook 앞단에서 처리). Supabase Edge Function이나 간단한 in-memory/Upstash Redis 카운터로 구현 가능.
- **전화번호 형식 검증**: 정규식으로 한국 휴대폰 번호 포맷만 허용.
- **필수 동의 없이 제출 차단**: 개인정보 수집 동의 체크 없이는 서버에서도 재검증(클라이언트 검증만으로는 우회 가능).

### 8.1 Supabase RLS(Row Level Security) 정책 방향

> [의견] 원본 문서들은 "Supabase에 저장한다"까지만 정의하고 접근 제어는 다루지 않았다. `leads`, `diagnoses`, `consultations`에는 이름·연락처·이메일 같은 개인정보가 그대로 들어가므로, RLS를 반드시 켜야 한다.

- 공개 진단/상담 제출 API는 `service_role` 키를 쓰는 서버 사이드(Next.js API Route 또는 n8n)에서만 insert하고, 브라우저에서 Supabase 클라이언트로 직접 insert하지 않는다(anon key 노출 시 테이블 스캔·대량 삽입 위험).
- 조회(select)는 관리자 인증 세션에서만 허용 — `diagnosis_results`를 결과 페이지에서 보여줄 때는 진단 제출 시 발급한 공개 식별자(UUID)로만 단건 조회되도록 별도의 제한적 RLS 정책(또는 API Route를 통한 프록시 조회)을 둔다.

## 9. AI 분석 파이프라인 (n8n)

### 9.1 처리 흐름

```
Next.js 진단 폼
   ↓ 폼 제출 (스팸 방어 통과)
서버 API Route
   ↓ 원본 데이터 저장 (status=SUBMITTED)
Supabase
   ↓
n8n Webhook 트리거
   ↓ status=PROCESSING
n8n → AI 모델 호출 (OpenAI 또는 Gemini)
   ↓
구조화된 JSON 결과 생성·검증
   ↓ 성공 시 status=COMPLETED / 실패 시 status=FAILED
Supabase 결과 저장
   ↓
결과 페이지 표시 + 관리자 Telegram 알림 + (P1) 고객 이메일 발송
```

### 9.2 AI 결과 JSON 스키마

```json
{
  "automationScore": 72,
  "priorityTasks": [
    {
      "name": "고객 문의 자동화",
      "reason": "월간 문의량이 많고 수동 확인 시간이 큽니다.",
      "difficulty": "낮음",
      "estimatedMonthlySavedHours": 12
    }
  ],
  "totalEstimatedSavedHours": { "min": 35, "max": 50 },
  "recommendedStack": ["Next.js Form", "n8n", "Supabase", "Telegram", "Gemini"],
  "implementationSteps": ["문의 데이터 수집", "담당자 알림 자동화", "AI 문의 분류", "답변 초안 생성"],
  "summary": "귀사는 고객 문의와 견적 업무부터 자동화하는 것이 효과적입니다."
}
```

예상 효과(절감 시간 등)는 항상 "입력값 기반 추정치"임을 결과 페이지에 명시한다. 세부 설계 전체를 무료 결과에 공개하지 않고, 우선순위·기대효과까지만 보여준 뒤 상담으로 연결한다.

### 9.3 JSON 출력 안정화 — 구체적 기술 방식

> [의견] 02번 문서는 "JSON 출력 안정화가 가장 오래 걸리는 구간"이라고 정확히 짚었지만 구체적인 해결 방법은 없었다. 아래는 실제로 그 구간을 줄이는 기술적 선택이다.

- **Structured Output 기능 사용**: OpenAI는 `response_format: {type: "json_schema", strict: true}`, Gemini는 `responseSchema` 옵션으로 모델이 스키마를 벗어난 JSON을 아예 생성하지 못하게 강제할 수 있다. 프롬프트로 "JSON만 출력하세요"라고 타이르는 방식보다 훨씬 안정적이며, 이 기능을 쓰면 엣지케이스 방어에 드는 시간이 크게 줄어든다.
- **서버 사이드 재검증**: n8n에서 AI 응답을 받은 즉시 Zod(또는 JSON Schema validator)로 한 번 더 검증한다. 검증 실패 시 1회 자동 재시도(retry) 후에도 실패하면 `status=FAILED`로 저장하고 관리자에게 즉시 Telegram 알림.
- **필드 단계적 안정화**: 7개 필드(준비도/우선업무/난이도/절감시간/추천스택/구축단계/요약) 전부를 한 번에 안정화하려 하지 말고, 초기 배포에는 핵심 4개(준비도, 우선 업무, 절감시간, 요약)만 안정화하고 나머지는 P1로 미루는 선택지를 열어둔다(02번 문서 제안 유지).

### 9.4 3주차 리스크 완화 — Mock 우선 전략

n8n Webhook 연결과 결과 페이지 UI는 AI 없이 고정된 더미 JSON으로 먼저 붙인다. 이렇게 하면 AI 프롬프트 튜닝이 끝나지 않아도 나머지 파이프라인(DB 저장 → 결과 페이지 → Telegram)은 이미 동작하는 상태가 되고, 여러 신규 통합을 동시에 디버깅하는 상황을 피할 수 있다. (자세한 일정 배치는 17장 참고.)

### 9.5 결과 실패 시 사용자 경험

> [의견] 원본 문서들은 `FAILED` 상태값은 정의했지만 그때 사용자에게 무엇을 보여줄지는 정의하지 않았다. 최소 아래를 결과 페이지에 구현한다.

- FAILED 상태에서는 "죄송합니다, 분석 중 문제가 발생했습니다. 담당자가 확인 후 직접 연락드리겠습니다"라는 안내와 함께 이미 입력한 연락처로 상담 신청 폼을 자동 프리필해 보여준다.
- 이 경우 관리자 알림에 `[진단 실패]` 태그를 붙여 사람이 수동으로 결과를 만들어줄 수 있게 한다 — 리드를 그냥 잃지 않는 최소한의 안전망이다.

## 10. 결과 페이지 & 상태 머신

진단 상태: `SUBMITTED → PROCESSING → COMPLETED` (정상) / `PROCESSING → FAILED` (오류, 9.5절 대응).

결과 페이지는 장문 텍스트가 아니라 구조화된 카드 형태로 자동화 준비도, 우선 추천 업무, 예상 절감 시간, 권장 시스템 구성, 다음 행동(상담 신청 / 결과 이메일 받기 / 다시 진단하기)을 보여준다.

### 11.3 서비스 유형 자동 태깅 (n8n 워크플로우)

상담 신청 시점에는 5개 서비스 중 어떤 유형 상담인지 분류되어 있지 않다. 이 분류를 상담 콜에서 즉흥적으로 하면 상담이 길어지고 견적 정확도가 떨어지므로, AI 분석 결과를 기반으로 n8n에서 자동 태깅해 관리자 화면에 가설값으로 표시한다.

```
AI 분석 결과의 recommended_stack / priorityTasks 확인
  → "n8n" 포함 + 홈페이지 무관 업무 위주        → n8n Automation
  → "Website" 관련 추천 또는 "홈페이지 없음" 응답 → Smart Website
  → "사내 문서 검색", "고객 상담 AI" 등 Agent성   → AI Agent
  → 항목 다양 + 예산 낮음("방향성 파악" 목적)     → AI Consulting
  → 그 외 일반 반복 업무 자동화(기본값)          → AI Automation
→ consultations.suggested_service_type 에 저장
→ Telegram 알림에 "추정 서비스 유형" 함께 표시
```

이 태그는 확정이 아니라 "상담 시작 전 가설"이다. 상담 중 12.4절 체크리스트로 검증한다.

## 12. 서비스별 과금·견적 체계

### 12.1 문제

5개 서비스가 상담 신청이라는 단일 출구로 합쳐지지만, 실제 과금 구조는 서비스마다 다르다. AI Automation(건별 자동화), n8n Automation(워크플로우 구축), Smart Website(홈페이지+자동화 결합), AI Agent(구축+운영), AI Consulting(진단·자문).

### 12.2 서비스별 과금 모델

| 서비스 | 과금 방식 | 참고 가격대(추정) |
|---|---|---|
| AI Automation | 프로젝트 단가(업무 1건 기준 패키지) | 1건당 150만~500만원 |
| n8n Automation | 프로젝트 단가(복잡도 기준) + 유지보수 월 구독 | 구축 100만~400만원 + 유지보수 월 10만~30만원 |
| Smart Website | 프로젝트 단가(고정 스코프) | 200만~600만원 |
| AI Agent | 프로젝트 단가(구축) + 월 구독(운영·API 사용량) | 구축 300만~800만원 + 월 20만~50만원 |
| AI Consulting | 시간 단가 또는 세션 단가 | 시간당 10만~15만원, 또는 1회 세션 30만~50만원 |

*가격대는 시장 벤치마크 없이 잡은 초기 추정치다. 첫 5~10건 계약 후 실측 원가·소요시간 기준으로 재조정한다.*

핵심 구분: **일회성 구축(프로젝트 단가)** vs **지속 운영(구독형)**. n8n Automation과 AI Agent는 구축 후 운영비가 반드시 발생하므로, 견적서에 "구축비"와 "월 운영비"를 항상 분리 표기한다 — 이 사업의 반복 매출(recurring revenue) 구조를 만들 수 있는 지점이다.

> [의견] AI Agent의 "월 20만~50만원" 운영비 산정 근거를 지금 명시해 둔다: 이건 임의의 숫자가 아니라 실제 AI API 사용량에 연동되어야 한다. 15.3절의 토큰 비용 추정을 근거로 견적 시점마다 실측·검증할 것 — 그렇지 않으면 사용량이 많은 고객에게서 손실이 날 수 있다.

### 12.4 상담 전 확인 체크리스트 (서비스 유형별)

진단 폼 5단계에서 예산 범위·도입 목적·업무량은 이미 수집된다. 상담 콜에서는 서비스 유형별로 아래만 추가 확인하면 견적까지 이어질 수 있다.

| 서비스 유형 | 상담 시 추가 확인 질문 |
|---|---|
| AI Automation | 자동화 대상 업무 개수 / 기존 시스템(ERP, CRM 등) 연동 필요 여부 / 데이터 정형화 여부 |
| n8n Automation | 연동할 외부 서비스 개수 / 실시간 처리 필요 여부 / 구축 후 직접 수정할 사람 유무(유지보수 계약 여부 결정) |
| Smart Website | 기존 홈페이지 유무·마이그레이션 필요 여부 / 콘텐츠 직접 준비 가능 여부 / 결제·예약 등 추가 기능 필요 여부 |
| AI Agent | 데이터 범위(사내 문서량) / 응답 정확도 요구 수준 / API 사용량 연동 월 운영비 변동을 이해하는지 |
| AI Consulting | 진단만 원하는지, 구축까지 이어갈 의향이 있는지 / 사내 실행 인력 유무 |

공통 질문: 예산 결정권자가 본인인지 / 의사결정까지 예상 기간 / 경쟁 견적을 받고 있는지.

### 12.5 견적서 표준 구조

1. 범위(Scope) — 자동화 업무 목록, 페이지 수, 연동 항목 수 등 구체적으로
2. 제외 범위(Out of scope) — 분쟁 예방
3. 기간 — 착수~완료 예상 주차
4. 금액 — 구축비 / 월 운영비(해당 시) 분리 표기
5. 결제 조건 — 계약금 30~40% / 완료 후 60~70% (소규모 업체 대상 4~6주 프로젝트 기준 권장)
6. 유지보수 조건 — 무상 보증 기간(예: 완료 후 2주), 이후 유상 대응 기준

## 13. 트래픽 획득 전략

기존 계획의 "블로그 3개 + GA4·Clarity"는 트래픽을 측정하는 도구이지 만드는 채널이 아니다. 아래는 채널을 냉정하게 재평가한 결과다.

핵심 재평가: **카카오톡 채널은 획득 채널이 아니라 리텐션 채널**이며(개설 시점 팔로워 0), **신규 블로그는 초기 4주 KPI에 기여하지 않는다**(검색 신뢰도 형성에 최소 3~6개월). 둘 다 트래픽 소스 목록에서 빼고 각각 CRM 보조 수단 / 장기 자산 구축 트랙으로 재배치한다.

### 13.1 채널별 평가

| 채널 | 비용 | 실행 가능성 | 첫 4주 기여도 | 우선순위 |
|---|---|---|---|---|
| 지인 네트워크 직접 컨택 | 0원 | 높음 | 높음 — 첫 리드 확보의 핵심 | 1순위 |
| 지역/업종 커뮤니티 | 0원 | 중간(스팸 리스크) | 중간 | 1순위 |
| 오프라인 네트워킹 | 0~소액 | 중간 | 낮음~중간(신뢰도는 높음) | 2순위 |
| 카카오톡 채널 | 0원 | 높음 | 거의 없음(리텐션용) | 재배치 |
| 네이버 파워링크 | CPC 500~2,000원(추정) | 높음 | 중간, 예산 비례 | 검증 후 2순위 |
| 메타 광고 | CPC 300~1,000원(추정) | 높음 | 중간 | 검증 후 2순위 |
| 블로그/SEO | 시간 비용 | 높음 | 거의 없음(3~6개월 지연) | 장기 트랙 |

*CPC는 시장 평균 추정치이며 실제 집행 전 소액 테스트로 재확인한다.*

### 13.2 채널별 실행 방법 요약

- **지인 네트워크**(1주차~): "홈페이지 만들어드릴게요"가 아니라 "무료 자동화 진단 5분이면 됩니다"로 접근, 진단 링크 직접 전달. 목표: 첫 2주 20~30명 컨택 → 5~10건 진단 시작.
- **지역/업종 커뮤니티**(1~2주차~): 네이버 카페·당근마켓 비즈니스 게시판·지역 단톡방에 정보성 콘텐츠(직접 광고 아님)로 접근.
- **오프라인 네트워킹**(3주차 이후): 상공회의소, 소상공인시장진흥공단, 창업지원센터.
- **카카오톡 채널**(1주차 개설): 진단 완료 후 채널 추가 유도 → 결과 요약 재발송, 이후 콘텐츠 재발송으로 재방문 유도.
- **유료광고**(검증 후 3주차~, 월 20~30만원): 무료 채널로 1~2주 실측한 뒤에만 집행 — 그래야 어떤 숫자가 광고 문제이고 어떤 숫자가 폼/카피 문제인지 구분 가능.
- **블로그/SEO**(지속): "트래픽 소스"가 아니라 "상담 전 신뢰 자료"로 목적을 바꿔 계속 작성.

### 13.3 첫 4주 실행 타임라인

| 주차 | 실행 항목 | 목표 |
|---|---|---|
| 1주차 | 지인 네트워크 리스트업 + 1차 컨택, 카카오톡 채널 개설 | 컨택 10건, 진단 시작 2~3건 |
| 2주차 | 지인 네트워크 2차 컨택, 커뮤니티 게시 2~3건 | 누적 진단 시작 8~12건 |
| 3주차 | 커뮤니티 지속, 오프라인 네트워킹 1회, 유료광고 소액 테스트 | 누적 진단 시작 15~20건, 광고 CAC 첫 측정 |
| 4주차 | 채널별 실측 데이터 정리·재조정 | 채널별 전환율 비교표 확보 |

이 표의 숫자는 목표가 아니라 관찰 대상이다. 실제 값이 크게 벗어나면 14.3절 임계값 기준으로 원인(랜딩페이지/폼/채널)을 구분해 조정한다.

**초기 트래픽 예산**: 4주 총 40~60만원(유료광고 소액 테스트 20~30만원 + 오프라인 행사비 등 여유 10~20만원). 무료 채널이 우선이므로 이 예산은 필수 집행액이 아니라 채널 검증용이다.

## 14. KPI

### 14.1 문제

진단 시작률 8%, 완료율 50%, 상담 전환율 15%, 계약 전환율 30%는 벤치마크·과거 데이터 없이 설정된 목표치다. 틀렸다는 게 아니라, 실측값이 낮게 나왔을 때 "무엇을 바꿀지" 기준이 없으면 숫자가 관리 도구로 기능하지 못한다.

### 14.2 초기 가설로 재정의

| 지표 | 재정의 |
|---|---|
| 방문자 대비 진단 시작률 | 초기 가설 8% — 최소 방문 100건 누적 전까지는 참고치 |
| 진단 시작 대비 완료율 | 초기 가설 50% — 5단계 이탈 추적이 이 숫자보다 중요 |
| 진단 완료 대비 상담 신청률 | 초기 가설 15% — 결과 페이지 품질·CTA에 직접 영향 |
| 상담 대비 계약 전환율 | 초기 가설 30% — 상담 10건 누적 전까지 통계적 의미 없음 |

**실측 기반 재설정**: 1~2주차 무료 채널로 최소 트래픽 확보 + GA4 이벤트 기록 → 3~4주차 누적 방문 100건 또는 진단 완료 10건 중 먼저 도달하는 시점에 1차 리뷰 → 매주 금요일 채널별·단계별 숫자를 표 하나로 기록(별도 대시보드 불필요) → 4~6주차 안정화되면 초기 가설을 실측 기반 목표로 교체.

### 14.3 임계값별 대응 기준

| 상황 | 원인 추정 | 대응 |
|---|---|---|
| 방문 100건 이상인데 진단 시작률 3% 미만 | 랜딩페이지 설득력 부족 | Hero 카피·CTA A/B 비교, 문제 제시 섹션 재점검 |
| 진단 시작 대비 완료율 30% 미만 | 특정 단계 이탈 집중 | GA4로 이탈 단계 특정 → 해당 단계 질문 수 축소 |
| 진단 완료 대비 상담 신청률 5% 미만 | 결과가 일반적/CTA 약함 | AI 프롬프트 구조화 강도 점검, CTA 문구·위치 변경 |
| 상담 후 계약 전환율 10% 미만(10건 이상 누적) | 견적가 미스매치/상담 스크립트 문제 | 12.4절 체크리스트 누락 여부 점검, 가격대 재검토 |

### 14.4 GA4 이벤트 설계 (P0)

완료율 하나로는 어디가 문제인지 알 수 없다. 진단 폼 5단계 각각에 이벤트를 건다.

```
step1_view / step1_complete
step2_view / step2_complete
step3_view / step3_complete
step4_view / step4_complete
step5_view / step5_submit
diagnosis_result_view
consultation_cta_click
consultation_submit
```

새 기능이 아니라 기존 폼에 이벤트 태그만 추가하면 되는 작업이라 일정에 미치는 영향은 거의 없다.

### 15.2 배포 구성 및 백업

> [의견] 원본 문서는 "Docker 배포 + DB 백업"이라고만 되어 있고 구체적인 구성이 없다. 최소한 아래는 배포 전에 정해야 한다.

- Docker Compose로 Next.js 앱 + n8n을 함께 구동, Nginx Proxy Manager로 리버스 프록시 + Let's Encrypt 인증서 자동 발급.
- Supabase는 클라우드 관리형을 그대로 쓰는 것을 권장(자체 Postgres 운영은 1인 체제에 부담) — 클라우드 관리형이면 백업은 Supabase 대시보드의 자동 백업(플랜에 따라 일 단위) 활용 + 주요 마일스톤 전에는 `pg_dump`로 수동 스냅샷을 추가로 받아둔다.
- n8n 워크플로우 정의(JSON)는 Git 저장소에 export해 버전 관리한다 — n8n 서버가 죽어도 워크플로우 자체는 복구 가능하게.

> [의견] Contabo VPS + Docker로 나머지 스택을 전부 self-host하면서 DB만 외부 Supabase에 두는 게 어색해 보일 수 있는데, 의도적인 선택이다. Supabase 오픈소스 전체 스택(Kong, GoTrue, PostgREST, Realtime, Storage, Studio 등 컨테이너 8~9개)을 같은 VPS에 얹으면 Next.js·n8n과 리소스를 나눠 써야 해서 소형 VPS엔 부담이 크고, 애초에 Supabase를 고른 이유("1인 운영자가 DB 백업·장애·보안 패치까지 떠안지 않게 함")와 정반대 결과가 된다. DB만 관리형으로 분리해두면 Contabo VPS가 죽어도 리드 데이터는 안전하고, VPS 쪽 장애 복구에만 집중하면 된다 — 이 비대칭 구성을 유지한다.

### 15.3 AI API 비용 추정 (신규)

> [의견] 어느 문서에도 AI 호출 비용이 없다. 대략적인 자릿수만 잡아둔다: 진단 1건당 프롬프트(회사정보+도구+업무+업무량, 약 500~1,000 토큰) + 응답 JSON(약 500~800 토큰) 기준, 저비용 모델(GPT-4o-mini급/Gemini Flash급) 사용 시 1건당 원가는 수십 원 수준으로, 진단 100건이 들어와도 월 API 비용은 만원 단위를 넘기 어렵다. 즉 초기 단계에서 AI API 비용은 사업성에 영향을 주는 변수가 아니다 — 예산 걱정보다 9.3절의 출력 안정화(품질) 쪽에 시간을 쓰는 게 맞다. 다만 AI Agent 서비스처럼 고객사가 대량의 문서를 넣고 상시 질의하는 구조가 되면 사용량이 완전히 달라지므로, AI Agent 월 운영비(12.2절)는 이 초기 진단 비용과 분리해서 별도로 실측해야 한다.

## 16. 보안·법적 준수 체크리스트

> [의견] 기존 문서는 "개인정보 수집 동의 + 개인정보처리방침"까지만 다루고, 실제로 이 서비스가 개인정보를 해외 AI 서버로 보낸다는 사실이 만드는 법적 의무는 다루지 않았다. 아래가 이번에 추가한 부분이다.

### 16.1 개인정보 국외 이전 고지 (중요)

진단 폼에는 이름·연락처·이메일이 포함되고, 이 데이터를 OpenAI/Gemini 같은 해외 AI 서비스에 전달해 분석한다면 이는 개인정보의 국외 이전에 해당할 수 있다. 두 가지 대응 방식이 있다.

1. **권장**: AI 호출 시점에 이름·연락처·이메일 등 직접 식별 정보는 제외하고, 업종·직원수·도구·업무 같은 "업무 데이터"만 AI에 전달한다. 개인 식별 정보는 Supabase에만 저장하고 AI 파이프라인에는 아예 노출시키지 않는 것이 가장 깔끔한 리스크 회피다 — 진단 결과 품질에도 영향이 없다(개인 식별 정보는 애초에 분석에 필요하지 않다).
2. 그럼에도 다른 개인정보 처리 과정에서 국외 인프라(예: 해외 리전 서버)를 거친다면, 개인정보처리방침에 국외 이전 관련 사항(이전받는 자, 이전 목적, 항목, 국가, 시기·방법, 보유·이용 기간)을 명시하고 별도 동의를 받아야 한다.

이 부분은 법률 자문이 아니라 실무적 제안이며, 실제 처리방침 문구는 변호사·노무사 등 전문가 검토를 받는 것을 권장한다.

### 16.2 이용약관

개인정보처리방침만으로는 상담·계약 과정에서 발생할 수 있는 책임 범위, 서비스 이용 조건을 다루지 못한다. 최소한의 이용약관 페이지도 P0~P1 사이에 함께 준비한다.

### 16.3 스팸 방어

7.4절 참고(허니팟, rate limit, 서버사이드 검증).

### 16.4 관리자 계정 보안

관리자 계정이 사실상 1개(사용자님 본인)이므로, 유출 시 전체 리드 데이터가 노출된다. 강력한 비밀번호 + 가능하면 Supabase Auth의 2FA(OTP) 옵션을 켠다.

### 16.5 최소 모니터링

별도 유료 모니터링 도구 없이도, 이미 구축하는 Telegram Bot 채널을 시스템 에러 알림 채널로 함께 쓴다 — n8n 워크플로우 실패, AI 응답 검증 실패(9.3절), API 다운타임 등을 같은 Telegram 채널(또는 별도 채널)로 즉시 받도록 구성. 1인 운영 체제에서는 이것만으로도 "장애를 몇 시간째 모르고 있었다"는 최악의 상황을 막을 수 있다.

4주를 고정 마감으로 취급하지 않고, P0 완료를 기준으로 유동적으로 운영한다.

| 주차 | 목표 | 비고 |
|---|---|---|
| 1주차 | IA·카피·와이어프레임, Next.js/Supabase 프로젝트 기반 구성 | — |
| 2주차 | 랜딩페이지, 진단 폼(7.4절 스팸 방어 포함), 유효성 검사, DB 저장, 반응형 | — |

| 3.5주차(버퍼, 필요시) | AI 출력 안정화 전용 기간 | 3주차 체크포인트에서 미완료 시에만 사용 |
| 4주차 | 관리자 화면, 상담 신청 연결(서비스 자동 태깅 포함), 개인정보처리방침(국외이전 고지 포함), GA4 5단계 이벤트 | SEO·블로그는 이 주차에서 제외 |
| 4주차 이후(지속) | 이메일 발송, 블로그 3개, SEO 메타데이터, Docker 배포, 백업, QA(17.1절) | P1 성격이 강한 항목을 유동 구간으로 이동 |

### 17.1 3주차 세부 분해와 체크포인트

| 작업 | 예상 소요 | 리스크 |
|---|---|---|
| n8n Webhook 연결 | 0.5일 | 낮음 |
| AI 프롬프트 설계 + 1차 JSON 출력 | 1일 | 중간 |
| JSON 출력 안정화(엣지케이스 방어) | 별도 배정 필요 | **높음 — 가장 오래 걸리는 구간** |
| 진단 결과 DB 저장 | 0.5일 | 낮음 |
| 결과 페이지 구현 | 1일 | 낮음~중간 |
| Telegram 알림 연동 | 0.5일 | 낮음 |

- **3주차 3일차 종료 시점**: n8n Webhook + 1차 AI 출력이 동작하지 않으면 → 즉시 스코프 축소(핵심 4개 필드만 안정화, 9.3절) → 4주차 SEO/블로그 작업을 5주차로 이동해 여유 확보.
- **3주차 종료 시점**: 결과 페이지까지 동작하지만 Telegram 알림이 안 붙었으면 → 4주차로 이월 가능(이메일도 이미 P1).

### 17.2 QA 체크리스트 (출시 전 최소 확인, 신규)

> [의견] 원본 문서에는 "전체 QA"라는 항목만 있고 무엇을 확인할지가 없었다. 최소 체크리스트를 명시한다.

- 진단 폼 5단계 Happy path 1회 전 구간(제출 → 결과 확인 → 상담 신청)이 실제로 끝까지 동작하는지
- 모바일(iOS Safari, Android Chrome) + 데스크톱 각 1회 반응형 확인
- 폼 필수값 누락, 전화번호 형식 오류, 중복 제출 시 오류 메시지가 정상 노출되는지
- AI 응답 실패(FAILED) 시나리오를 의도적으로 발생시켜 9.5절 대응 흐름이 동작하는지
- Telegram 알림이 신규 진단·신규 상담·시스템 에러 세 경우 모두 정상 도착하는지
- 개인정보 동의 없이는 서버에서도 제출이 거부되는지(클라이언트 우회 테스트)

### 17.3 실제 소요시간 기록

3주차뿐 아니라 전체 개발 기간의 실제 소요시간을 매일 기록한다. 이 기록은 다음 프로젝트(2번째 서비스 구축 등) 견적 산정에 그대로 쓰인다.
