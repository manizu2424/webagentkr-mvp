# 인프라 배포 운영 가이드

2026-09-18에 Contabo VPS에 `main` 브랜치를 처음 실배포하면서 만든 인프라를 사용자가 직접 관리할 수 있도록 정리한 문서. "무엇을 했는지"와 "어떻게 쓰는지"를 다룬다. 실제 비밀번호·키는 이 파일에 없다 — `docs/자격증명_비공개.md`(git에 안 올라감) 참고.

## 1. 오늘 한 일 요약

- **VPS 구매·보안 세팅**: Contabo Cloud VPS 4(4vCPU/8GB, Asia Japan, Ubuntu 24.04.5 LTS), IP `84.247.155.90`. root 비밀번호 로그인은 SSH 키 인증으로 전환 후 비활성화.
- **Docker 배포**: `ufw`로 22/80/443만 허용 → 리포 `main`(커밋 `7b86587`) clone → `docker compose build && up -d`로 `web`·`n8n`·`nginx-proxy-manager` 기동.
- **도메인 연결**: 이미 보유 중이던 `webagent.kr`이 이 VPS IP를 가리키고 있어 그대로 사용. Nginx Proxy Manager(NPM)에서 `webagent.kr → web:3000` 프록시 호스트 생성 + Let's Encrypt 인증서 발급.
- **n8n 실제 연동**: `n8n/workflows/SETUP.md` 절차대로 credential 4종(Header Auth·OpenAI·Supabase·Telegram) 생성, `diagnosis-pipeline`·`error-trigger` 워크플로우 import 및 활성화. `N8N_WEBHOOK_URL`은 Docker 내부망 주소(`http://n8n:5678/...`)로 설정해 **n8n을 인터넷에 전혀 노출하지 않음** — OpenAI/Supabase 키를 들고 있는 서비스라 이게 핵심 보안 포인트.
- **전 구간 실증**: 진단 폼 제출 → n8n → GPT-4o → 결과 페이지까지 5.8초, 상담 폼 제출, Telegram 알림 수신(로컬 PC에서 IPv6 문제로 못 봤던 부분, VPS에서 최초 확인)까지 실제 확인함.
- **Docker 빌드 갭 수정**: `.env.example`엔 있었지만 `Dockerfile`/`docker-compose.yml`의 build args에 빠져 있던 `NEXT_PUBLIC_SITE_URL`·`NEXT_PUBLIC_CLARITY_PROJECT_ID` 추가 (PR #19).
- **DB 백업 + 복원 검증**: `pg_dump` 크론(매일 03:00 KST, 7일 로테이션) 등록, 수동 실행 성공, 로컬 임시 컨테이너에 복원해 `leads`/`diagnoses`/`diagnosis_results`/`consultations` row count가 실 Supabase와 **완전 일치** 확인.
- **Portainer 설치**: 컨테이너 관리를 웹 UI로도 할 수 있게 설치·초기 설정 완료.
- **n8n·Portainer 공개 서브도메인화**: `https://n8n.webagent.kr`, `https://portainer.webagent.kr`을 NPM 프록시 + Let's Encrypt로 연결. 이제 SSH 터널 없이 브라우저로 바로 접속 가능 (각자 자체 로그인으로 보호됨). NPM 관리 화면(포트 81) 자체만 여전히 SSH 터널 전용.

## 3. 매일 쓰는 명령어

### SSH 접속
이 Mac에서는 별칭이 등록되어 있어 바로 접속된다.
```bash
ssh webagent-vps
```

### 재배포 (코드 변경 반영)
```bash
ssh webagent-vps
cd /opt/webagent/app
git pull
docker compose up -d --build
```

### 컨테이너 상태·로그
```bash
ssh webagent-vps "cd /opt/webagent/app && docker compose ps"
ssh webagent-vps "docker logs -f app-web-1"        # Next.js 로그
ssh webagent-vps "docker logs -f app-n8n-1"        # n8n 로그
ssh webagent-vps "docker logs -f app-nginx-proxy-manager-1"
```

### 재시작
```bash
ssh webagent-vps "cd /opt/webagent/app && docker compose restart web"
```

### `.env`/`n8n.env` 값을 바꿨을 때
env 파일 내용을 바꿔도 실행 중인 컨테이너는 자동 반영이 안 된다 — 재생성 필요:
```bash
ssh webagent-vps "cd /opt/webagent/app && docker compose up -d --force-recreate web"
```

## 4. 관리 화면 사용법

| 화면 | 접속 방법 | 로그인 정보 |
|---|---|---|
| n8n | `https://n8n.webagent.kr` (바로 접속) | `docs/자격증명_비공개.md` |
| Portainer | `https://portainer.webagent.kr` (바로 접속) | `docs/자격증명_비공개.md` |
| NPM 관리 화면 | SSH 터널 전용(아래) | `docs/자격증명_비공개.md` |

n8n·Portainer는 각자 자체 로그인으로 보호되는 공개 서브도메인이라 브라우저로 바로 열면 된다. NPM의 관리 화면(포트 81)만 인터넷에 공개하지 않고 SSH 터널로 연다:

```bash
ssh -N -L 8181:127.0.0.1:81 webagent-vps
```
켜둔 채로 브라우저에서 `http://localhost:8181` 접속. 터미널 창을 닫으면 터널도 끊긴다.

### NPM (Nginx Proxy Manager)
새 서비스를 도메인에 연결하고 싶을 때: Hosts → Proxy Hosts → Add Proxy Host. Forward Hostname에는 `docker-compose.yml`/`docker run --network app_default`의 서비스·컨테이너명(예: `web`, `n8n`, `portainer`)을 그대로 쓰면 된다(같은 Docker 네트워크라 IP 몰라도 이름으로 통신됨). 새 서브도메인을 쓰려면 먼저 도메인 DNS에 A레코드(또는 이미 등록된 와일드카드 `*.webagent.kr`)가 있어야 하고, 레코드를 막 추가했다면 Let's Encrypt 인증서 발급이 DNS 전파 지연으로 한동안(최대 몇 시간) 실패할 수 있다 — 실패하면 나중에 Edit → SSL 탭에서 재요청.

### n8n
워크플로우 확인·수정·실행 로그(Executions)는 전부 이 화면에서. `WEBAGENT — diagnosis pipeline`이 진단 파이프라인, `WEBAGENT — error trigger`가 에러 발생 시 텔레그램 알림 워크플로우. **둘 다 켜진(Published) 상태여야 정상 동작.**

### Portainer
컨테이너를 CLI 없이 GUI로 보고 싶을 때. 좌측 `local` 환경 클릭 → Containers에서 재시작/로그/셸 접속 전부 가능.

## 5. DB 백업 / 복원

### 백업
- 스크립트: VPS 안 `/opt/backups/webagent/backup.sh`
- 매일 03:00 KST(UTC 18:00) 자동 실행, `/opt/backups/webagent/webagent-YYYY-MM-DD.dump`로 저장, 7일 지난 파일은 자동 삭제
- 수동 실행: `ssh webagent-vps "/opt/backups/webagent/backup.sh"`
- 로그: `ssh webagent-vps "cat /opt/backups/webagent/backup.log"`

### 복원 (재해 시)
```bash
# 1. VPS에 임시 Postgres 컨테이너 기동
ssh webagent-vps "docker run -d --name pg-restore -e POSTGRES_PASSWORD=temp postgres:17-alpine"

# 2. 원하는 날짜의 덤프를 복사
ssh webagent-vps "docker cp /opt/backups/webagent/webagent-<날짜>.dump pg-restore:/tmp/backup.dump"

# 3. 복원
ssh webagent-vps "docker exec pg-restore pg_restore -U postgres -d postgres --no-owner --no-acl /tmp/backup.dump"

# 4. 확인 후 정리
ssh webagent-vps "docker rm -f pg-restore"
```
실제 Supabase로 되돌려야 하는 재해 상황이면, 3번 대상을 로컬 임시 DB 대신 Supabase 연결 문자열로 바꿔서 실행(단, 기존 데이터를 덮어쓰므로 신중히).

## 6. 트러블슈팅

| 증상 | 확인할 것 |
|---|---|
| 사이트가 안 뜸 | `docker compose ps`로 컨테이너 살아있는지, `docker logs app-web-1`로 에러 확인 |
| 진단 제출 후 "분석 중"에서 안 넘어감 | n8n Executions에서 마지막 실행이 실패했는지 확인. 워크플로우가 Published(Active) 상태인지 확인 |
| Telegram 알림이 안 옴 | n8n credential의 Telegram bot 토큰, `n8n.env`의 `TELEGRAM_ADMIN_CHAT_ID`/`TELEGRAM_ERROR_CHAT_ID` 확인 |
| 인증서 만료 임박 | NPM이 자동 갱신하지만, Certificates 메뉴에서 만료일 확인 가능. 실패 시 Let's Encrypt rate limit이나 DNS 문제일 수 있음 |
