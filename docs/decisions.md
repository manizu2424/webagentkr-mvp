## D1 — 진단 폼 누락 필드 3개 (결함 #6, #7)

기획서 §7이 요구하지만 DDL·API 어디에도 없는 필드가 3개다. 각각 추가할지 폼에서 뺄지 결정해야 한다.

| 필드 | 위치 | 권장 | 근거 |
|---|---|---|---|
| **도입 목적** | 5단계 | ✅ **추가 (필수)** | 기획서 §11.3 자동 태깅 규칙이 `"방향성 파악" 목적 → AI Consulting` 분기에서 이 값을 직접 사용한다. 없으면 5개 분기 중 하나가 구현 불가. |
| **담당 인원** | 4단계 | ✅ **추가 (권장)** | 절감 시간 추정의 핵심 변수. "하루 4시간"이 1명인지 3명인지에 따라 월 절감 시간이 3배 차이 난다. AI 프롬프트(§7.2) 품질에 직접 기여. |
| **현재 처리 방식** | 4단계 | ❌ **제거 (권장)** | 2단계 "사용 도구"(Excel/이메일/카카오톡/ERP…)와 사실상 중복. 자유 텍스트로 받으면 §16.1의 PII 유입 경로가 하나 더 늘어난다. `pain_point` 자유 텍스트로 충분히 커버된다. |

**추가 시 스키마 변경** (`diagnoses` 테이블):
```sql
purpose      text,   -- 도입 목적 (D2 선택지)
staff_count  text,   -- 담당 인원 (D2 선택지)
```
API 바디에 `purpose`, `staffCount` 추가. **둘 다 PII가 아니므로 n8n 웹훅 페이로드에도 포함**한다(§16.1 위반 아님) — 오히려 AI 분석 품질을 올린다.

> **결정 (2026-09-04, 확정):** 권장안대로. `diagnoses`에 `purpose`, `staff_count` 컬럼 추가.
> **현재 처리 방식**은 폼에서 제거 — 기획서 §7 4단계 항목 목록에서 빠진다.
> 두 신규 필드는 n8n 웹훅 페이로드에도 포함하고, AI 프롬프트(§7.2)에 `도입 목적`/`담당 인원` 줄을 추가한다.

## D2 — select 선택지 값 전체 (결함 #10)

DDL 주석은 `"select 옵션과 1:1로 맞출 것"`이라 요구하지만 목록이 어느 문서에도 없다. 이 값들은 DB에 **문자열 그대로** 저장되므로, 나중에 바꾸면 기존 행이 깨진다. 지금 확정해야 한다.

### D2-a. 저장 형식

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. 한글 라벨 그대로 저장** (권장) | 스펙 DDL 주석과 일치. AI 프롬프트(§7.2)가 `{{employeeCount}}`를 그대로 한국어 문장에 넣으므로 변환 불필요. 관리자 화면도 그대로 표시. | 라벨 문구를 바꾸면 데이터 마이그레이션 필요 |
| B. 코드 저장 + 라벨 매핑 (`EMP_5_10`) | 문구 변경이 자유로움 | AI 프롬프트·관리자 화면 양쪽에 역매핑 필요. MVP에 과함 |

권장: **A**. 단, 모든 값을 `lib/options.ts` 한 곳에만 정의하고 폼·validation·태깅이 전부 거기서 참조한다(하드코딩 금지).

### D2-b. 선택지 값 (권장안)

```ts
// 업종 — 기획서 §2 초기 집중 업종 우선순위 순
industry: ["건설·인테리어", "부동산", "전문서비스(법무·세무·회계·노무)", "교육·학원",
           "컨설팅", "제조", "유통·도소매", "의료·보건", "IT·소프트웨어",
           "요식·숙박", "1인 기업·프리랜서", "기타"]

// 직원 수 — 타깃은 5~50명이나 1인 기업도 타깃(§2)이므로 하단 구간 포함
employeeCount: ["1-4명", "5-10명", "11-30명", "31-50명", "51-100명", "100명 이상"]

// 홈페이지 유무
websiteStatus: ["없음", "있음 (운영 중)", "있으나 방치 상태", "제작·개편 예정"]

// 하루 반복 업무 시간
dailyHours: ["1시간 미만", "1~2시간", "2~4시간", "4~6시간", "6시간 이상"]

// 담당 인원 (D1에서 추가 시)
staffCount: ["1명", "2~3명", "4~5명", "6명 이상"]

// 월간 처리 건수
monthlyVolume: ["50건 미만", "50~200건", "200~500건", "500~1,000건", "1,000건 이상", "파악 못함"]

// 도입 목적 (D1에서 추가 시) — "방향성 파악"이 §11.3의 AI Consulting 분기를 구동
purpose: ["업무 시간 절감", "인건비 절감", "고객 응대 속도 개선",
          "데이터 관리 체계화", "방향성 파악 (무엇부터 할지 모름)", "기타"]

// 예산 범위 — 기획서 §12.2 가격대(150만~800만원)와 정합
budgetRange: ["미정 (방향성부터 파악)", "300만원 미만", "300~500만원",
              "500~1,000만원", "1,000만원 이상"]

// 상담 방식 — leads.consulting_method / consultations.consultation_type 공용
consultingMethod: ["전화", "온라인 미팅", "방문 상담", "이메일"]

// 희망 상담 시기 — consultations.preferred_date
preferredDate: ["가능한 빨리", "1주일 이내", "2주일 이내", "1개월 이내"]
```

이미 정의된 것(기획서 §7, 변경 없음): `currentTools` 11종, `repetitiveTasks` 10종.

### D2-c. 확인 필요한 중복

`leads.consulting_method`(진단 5단계 "상담 방식")와 `consultations.consultation_type`(상담 폼)이 **같은 의미로 보인다.** 위 권장안은 같은 값 집합을 공유하도록 했다. 별개 의미가 맞다면 알려달라 — 아니면 `consultation_type` 컬럼을 지우는 게 맞다.

> **결정 (2026-09-04, 확정):** 권장안대로. D2-a는 **A(한글 라벨 저장)**, D2-b 목록은 위 초안 그대로 `lib/options.ts`에 단일 정의.
> D2-c는 두 컬럼을 **유지하되 같은 값 집합(`consultingMethod`)을 공유**한다 — 진단 시점 희망(`leads.consulting_method`)과 상담 확정 방식(`consultations.consultation_type`)이 달라질 수 있으므로 컬럼은 남긴다.
> ⚠️ 이후 라벨 문구 변경은 데이터 마이그레이션을 동반한다.

## D3 — 서비스 자동 태깅을 어디서 계산할지 (결함 #8)

세 절이 서로 다른 말을 한다. 기획서 §11.3은 n8n이 진단 시점에, 기술 스펙 §4.3은 "`diagnoses`에서 가져와"(그런 컬럼 없음), 기술 스펙 §6의 노드 목록에는 아예 없다. **진단 시점에는 `consultations` 행이 존재하지 않으므로 §11.3 그대로는 불가능하다.**

| 옵션 | 내용 | 평가 |
|---|---|---|
| **A. 상담 신청 시점에 Next.js에서 계산** (권장) | `POST /api/consultations`에서 `diagnosis_results`를 읽어 `lib/serviceTagging.ts`로 판정 → `consultations.suggested_service_type` 저장 | 규칙이 상담 경험에 따라 자주 바뀔 텐데 TS 코드가 n8n UI보다 수정·테스트가 쉽다. §6 워크플로우를 단순하게 유지. 컬럼 추가 불필요. |
| B. n8n이 진단 시점에 미리 계산해 `diagnosis_results`에 저장 | 새 컬럼 + n8n 노드 추가, 상담 시 복사 | AI 결과와 함께 보관되는 건 장점이나, 규칙 변경마다 워크플로우 재배포. 상담이 없는 진단에도 태그가 생김(무해하나 불필요) |

어느 쪽이든 §11.3 규칙은 D1의 **도입 목적** 필드가 있어야 완전해진다.

> **결정 (2026-09-04, 확정):** **옵션 A**. `lib/serviceTagging.ts`에서 상담 신청 시점에 계산.
> 기획서 §11.3(n8n이 계산)과 기술 스펙 §4.3("diagnoses에서 가져와")은 이 결정으로 대체된다.
> 기술 스펙 §6의 n8n 워크플로우에는 태깅 노드를 추가하지 않는다.

## D4 — `diagnosis_results.difficulty` 컬럼 처리 (결함 #9)

DDL에 `difficulty text` 컬럼이 있으나 **AI 출력(§7.3)에 대응하는 최상위 필드가 없다.** §7.3의 `difficulty`는 `priorityTasks[]` 배열 **안쪽** 필드이고, 기획서 §9.2 예시 JSON에도 최상위 난이도는 없다.

| 옵션 | 평가 |
|---|---|
| **A. 컬럼 삭제** (권장) | 결과 페이지는 업무별 난이도를 카드로 보여주므로 "전체 난이도"를 표시할 자리가 없다. 업무별 값은 `recommended_tasks` jsonb 안에 이미 있다. |
| B. 유지하고 파생값 계산 | n8n에서 `priorityTasks`의 최빈값 또는 최고 난이도를 넣음. 의미가 모호해 관리자에게도 쓸모가 적다. |
| C. AI 스키마에 최상위 `difficulty` 추가 | 필드가 하나 늘어 §9.3의 "핵심 4개 먼저 안정화" 전략과 역행 |

> **결정 (2026-09-04, 확정):** **옵션 A**. `diagnosis_results.difficulty` 컬럼을 `0001_init.sql`에서 제외.
> 난이도는 `recommended_tasks` jsonb 안의 업무별 `difficulty`(`낮음|중간|높음`)로만 다룬다.

## D5 — Supabase 플랜과 백업 방식 (결함 #18)

기획서 §4는 **"Docker 기반 배포 + DB 백업"을 P0 출시 필수**로 두고, §15.2는 "Supabase 대시보드의 자동 백업(플랜에 따라 일 단위)"이라고 쓴다. 그런데 **Free 플랜에는 자동 백업이 없다.** 리드 데이터가 이 사업의 전부이므로 회피 불가한 결정이다.

| 옵션 | 비용 | RPO | 비고 |
|---|---|---|---|
| **A. Free + cron `pg_dump`** (권장) | 0원 | 24시간 | 이미 있는 Contabo VPS에서 일 1회 덤프, 7일 로테이션, 오프사이트 복사. Free는 미사용 시 프로젝트 일시정지 정책이 있으나 실 운영 중이면 해당 없음. **덤프·복원 스크립트를 P0에서 실제로 검증해야 함** |
| B. Pro 전환 | 약 $25/월 (≈3.5만원) | 24시간 + PITR 옵션 | 일 자동 백업 7일 보관, 일시정지 없음. 기획서 §3 비용표(서버비 1.5~3만원)가 약 2배가 된다 |

권장: **A로 출시 → 첫 계약 성사 후 B 전환.** 어느 쪽이든 기획서 §3 비용 체크리스트에 "백업" 항목을 추가해야 한다(현재 없음).

> **결정 (2026-09-04, 확정):** **옵션 A**. Supabase Free + Contabo VPS cron `pg_dump`(일 1회, 7일 로테이션, 오프사이트 복사).
> 전환 트리거: **첫 계약 성사 시 Pro($25/월)로 전환.**
> Phase 4.5에서 덤프 스크립트와 **복원 절차까지 실제로 검증**해야 완료 처리한다 — 덤프만 돌고 복원이 안 되는 백업은 백업이 아니다.

## 추가 기록 (2026-09-07) — `leads` upsert "마지막 연락처가 이긴다" (결함 #11 / 최종 리뷰 I3)

`POST /api/diagnoses` 의 `leads` upsert 는 `onConflict: "email"` 을 쓴다(스펙 §5.1 6단계·결함 #11 이 재방문자 500 방지를 위해 명시). 시맨틱은 **"마지막 연락처가 이긴다"** — 같은 이메일(공용 메일함 `info@`·`ceo@` 등)로 다른 담당자가 재제출하면 `contact_name`·`phone`·`company_name`·`consulting_method` 가 덮어써지고, 먼저 접수된 `diagnoses` 행이 다른 사람의 연락처와 묶일 수 있다(`leads` 에 이력·`updated_at` 없음).

> **결정 (2026-09-07, 최종 리뷰):** 쿼리 동작은 **변경하지 않는다**(docs-only). 스펙·결함 #11 요구사항인 재방문자 500 방지를 유지. 코드(`app/api/diagnoses/route.ts` leads upsert 위 주석)·`task.md` Phase 1 이탈·메모에 한계로 명시.
> **post-MVP 방향:** `leads` 를 제출 단위 append-only 로 전환하고 email 디둡은 관리자/리포트 계층에서 수행.
