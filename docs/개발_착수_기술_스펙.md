이 문서는 `개발자용_통합_MVP_기획서.md`(제품·기능·사업 스펙)의 동반 문서다. 그 문서가 "무엇을 왜 만드는지"를 정의한다면, 이 문서는 "지금 에디터를 열고 무엇부터 타이핑할지"를 정의한다. 두 문서는 서로를 참조하며, 이 문서의 섹션 번호는 기획서의 관련 절을 함께 표기한다.

## 3. DB DDL (Supabase SQL Editor에서 실행)

기획서 8장의 필드 목록을 실제 타입까지 갖춘 마이그레이션으로 구체화했다. 기획서에 없던 추가 사항은 굵게 표시했다.

```sql
-- 확장
create extension if not exists "pgcrypto";

-- updated_at 자동 갱신 함수
create or replace function set_updated_at()
returns trigger as $$
begin
  new.updated_at = now();
  return new;
end;
$$ language plpgsql;

-- leads
create table leads (
  id uuid primary key default gen_random_uuid(),
  company_name text not null,
  industry text not null,
  employee_count text not null,          -- 예: "5-10명" 같은 구간값. select 옵션과 1:1로 맞출 것
  contact_name text not null,
  email text not null,
  phone text not null,
  consulting_method text,                -- 상담 희망 방식
  created_at timestamptz not null default now()
);

-- diagnoses
create table diagnoses (
  id uuid primary key default gen_random_uuid(),   -- 결과 페이지 공개 식별자로 그대로 사용 (UUID라 추측 불가)
  lead_id uuid not null references leads(id) on delete cascade,
  website_status text,
  current_tools text[] not null default '{}',
  repetitive_tasks text[] not null default '{}',
  daily_hours text,
  monthly_volume text,
  pain_point text,
  budget_range text,
  status text not null default 'SUBMITTED'
    check (status in ('SUBMITTED','PROCESSING','COMPLETED','FAILED')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create trigger diagnoses_set_updated_at
  before update on diagnoses
  for each row execute function set_updated_at();
create index idx_diagnoses_lead_id on diagnoses(lead_id);

-- diagnosis_results (1:1)
create table diagnosis_results (
  id uuid primary key default gen_random_uuid(),
  diagnosis_id uuid not null unique references diagnoses(id) on delete cascade,
  automation_score smallint check (automation_score between 0 and 100),
  recommended_tasks jsonb not null,       -- [{name, reason, difficulty, estimatedMonthlySavedHours}]
  estimated_saved_hours jsonb,            -- {min, max}
  difficulty text,
  recommended_stack text[],
  implementation_steps text[],
  ai_summary text,
  created_at timestamptz not null default now()
);

-- consultations
create table consultations (
  id uuid primary key default gen_random_uuid(),
  lead_id uuid not null references leads(id) on delete cascade,
  diagnosis_id uuid references diagnoses(id),   -- **추가: 어느 진단에서 넘어온 상담인지 추적 (기획서 원본엔 없었음)**
  suggested_service_type text
    check (suggested_service_type in
      ('AI Automation','n8n Automation','Smart Website','AI Agent','AI Consulting')),
  preferred_date text,
  consultation_type text,
  status text not null default 'NEW'
    check (status in ('NEW','CONTACT_PENDING','SCHEDULED','PROPOSAL_SENT','CONTRACTED','ON_HOLD','CLOSED')),
  memo text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create trigger consultations_set_updated_at
  before update on consultations
  for each row execute function set_updated_at();
create index idx_consultations_lead_id on consultations(lead_id);

-- **추가: 스팸 방어용 제출 로그 (7.4절 rate limit을 DB 기반으로 할 경우에만 필요, 4.2절 참고)**
create table submission_log (
  id bigserial primary key,
  ip text not null,
  created_at timestamptz not null default now()
);
create index idx_submission_log_ip_created on submission_log(ip, created_at);
```

### 3.1 RLS 정책

```sql
alter table leads enable row level security;
alter table diagnoses enable row level security;
alter table diagnosis_results enable row level security;
alter table consultations enable row level security;
alter table submission_log enable row level security;

-- anon 롤: 정책을 하나도 만들지 않는다 = 브라우저에서 anon key로는 아무것도 못 읽고 못 쓴다.
-- 모든 읽기/쓰기는 서버(Next.js API Route, n8n)가 service_role 키로 수행 → RLS 자동 우회.

-- authenticated 롤(=관리자, 회원가입 비활성화로 사실상 1계정): 관리자 화면에서 Supabase 클라이언트로 직접 조회
create policy admin_select_leads on leads for select to authenticated using (true);
create policy admin_select_diagnoses on diagnoses for select to authenticated using (true);
create policy admin_update_diagnoses on diagnoses for update to authenticated using (true);
create policy admin_select_results on diagnosis_results for select to authenticated using (true);
create policy admin_select_consultations on consultations for select to authenticated using (true);
create policy admin_update_consultations on consultations for update to authenticated using (true);
```

> Supabase Auth 설정에서 **회원가입(Sign up) 자체를 비활성화**해야 위 `authenticated using (true)` 정책이 안전하다 — 그렇지 않으면 누구나 가입해서 관리자 데이터를 읽을 수 있다. 대시보드 > Authentication > Providers에서 Email 가입을 끄고, 관리자 계정 하나만 Supabase 대시보드에서 직접 생성한다.

## 4. API 계약 (Next.js)

### 4.1 `POST /api/diagnoses`

공개, 스팸 방어 적용(4.2절). n8n을 직접 호출하지 않고 Supabase에만 쓰면, 상태 전이는 n8n이 Supabase에 직접 쓰는 방식(6장)을 쓰므로 이 라우트는 초기 저장 + n8n 트리거만 담당한다.

```
Request Body:
{
  companyName, industry, employeeCount, websiteStatus,
  currentTools: string[], repetitiveTasks: string[],
  dailyHours, monthlyVolume, painPoint, budgetRange,
  consultingMethod, contactName, email, phone,
  consentAgreed: boolean,
  hp_field: string          // 허니팟, 항상 빈 문자열이어야 함
}

처리 순서:
1. hp_field가 비어있지 않으면 → 200 OK 반환하되 아무 것도 저장하지 않음 (봇에게 신호 주지 않음)
2. consentAgreed !== true 면 → 400
3. rate limit 체크 (4.2절) 초과 시 → 429
4. leads insert (service_role) → lead_id 획득
5. diagnoses insert (status=SUBMITTED) → diagnosis_id 획득
6. N8N_WEBHOOK_URL로 POST, 헤더 X-Webhook-Secret 포함, 바디는 **PII 제외**(16.1절):
   { diagnosisId, industry, employeeCount, websiteStatus, currentTools,
     repetitiveTasks, dailyHours, monthlyVolume, painPoint, budgetRange }
7. diagnoses.status를 PROCESSING으로 업데이트
8. 응답: { diagnosisId }  →  클라이언트는 /diagnosis/[diagnosisId]로 이동
```

### 4.2 `GET /api/diagnoses/[id]`

공개, 결과 페이지 폴링용. service_role로 조회 후 필요한 필드만 골라 반환(내부 lead 정보는 절대 포함하지 않음).

```
Response (status=PROCESSING): { status: "PROCESSING" }
Response (status=COMPLETED):  { status: "COMPLETED", result: { automationScore, priorityTasks, totalEstimatedSavedHours, recommendedStack, implementationSteps, summary } }
Response (status=FAILED):     { status: "FAILED" }   // 9.5절 폴백 UI 트리거
```

프론트는 이 엔드포인트를 3초 간격으로 폴링하다가 `COMPLETED`/`FAILED`가 오면 멈춘다.

### 4.3 `POST /api/consultations`

공개, 스팸 방어 적용. `diagnosisId`는 결과 페이지에서 넘어온 경우에만 존재(옵셔널).

```
Request Body:
{ diagnosisId?, leadId 또는 (companyName, contactName, email, phone 등 재입력),
  preferredDate, consultationType, hp_field }

처리: 허니팟/rate limit 체크 → leads upsert(이미 진단에서 만든 lead면 재사용) →
      diagnosisId가 있으면 diagnoses에서 suggested_service_type 계산 로직 결과를 가져와 저장(11.3절) →
      consultations insert (status=NEW) → Telegram 알림
```

### 4.4 관리자 화면

별도 API 레이어 없이 Supabase 클라이언트(`lib/supabase/client.ts`, 로그인 세션 포함)로 3.1절 RLS 정책을 통해 직접 조회·업데이트한다 — 관리자 CRUD 전용 API 라우트를 따로 만들지 않아 개발량을 줄인다.

## 5. 스팸 방어 구현 (기획서 7.4절 구체화)

- **허니팟**: 폼에 `hp_field`라는 hidden input 추가. `display:none` 대신 `position:absolute; left:-9999px` + `tabIndex={-1}` + `aria-hidden="true"`로 처리(일부 봇은 `display:none`만 걸러냄).
- **Rate limit**: Docker 컨테이너 하나로 단일 인스턴스 배포하는 구성이므로, 별도 Redis(Upstash 등 외부 서비스)를 추가로 들이지 않고 **Next.js 서버 프로세스 내 in-memory Map**으로 시작한다 — `lib/rateLimit.ts`에서 `Map<ip, timestamp[]>`를 유지하고 시간당 5건 초과 시 차단. 컨테이너 재시작 시 카운터가 초기화되는 건 MVP 단계에서는 감수 가능한 트레이드오프다. 나중에 인스턴스를 여러 개로 늘리게 되면(현재 계획엔 없음) 그때 3장의 `submission_log` 테이블 기반이나 외부 스토어로 전환한다.

## 6. n8n 워크플로우 설계

기획서 9.1절 흐름을 실제 노드 단위로 분해했다. n8n이 Supabase에 직접 쓰기 때문에 Next.js 쪽에 콜백 API가 필요 없다(4장 참고).

```
[Webhook Trigger]  POST, X-Webhook-Secret 헤더 검증
   ↓
[Code 노드] 입력값 정리/포맷팅 (PII는 애초에 안 들어옴 — 4.1절 6번)
   ↓
[AI 노드] OpenAI/Gemini HTTP Request, Structured Output 스키마 적용 (7장)
   ↓
[Code 노드] 응답 필드 존재 여부 검증 (필수 필드 누락 시 실패 처리)
   ↓
[IF 노드] 검증 통과?
   ├─ Yes → [Supabase 노드] diagnosis_results insert
   │         → [Supabase 노드] diagnoses.status = 'COMPLETED'
   │         → [Telegram 노드] "신규 진단 완료: {company}" 알림
   └─ No  → [Supabase 노드] diagnoses.status = 'FAILED'
             → [Telegram 노드] "[진단 실패] {diagnosisId} 확인 필요" 알림
```

- 별도로 **Error Trigger 워크플로우**를 하나 더 만들어 위 워크플로우 전체(Webhook 호출 실패, AI API 다운타임 등)에 연결하고, 실패 시 `TELEGRAM_ERROR_CHAT_ID`로 알림을 보낸다(기획서 16.5절 최소 모니터링).
- 워크플로우 완성 후 JSON으로 export해 `n8n/workflows/diagnosis-pipeline.json`에 커밋한다(15.2절).
- Code 노드에서 zod 같은 외부 패키지를 쓰려면 n8n 컨테이너 환경변수에 `NODE_FUNCTION_ALLOW_EXTERNAL=zod`를 추가해야 한다(8장 docker-compose 참고). MVP 초기엔 zod 없이 단순 필드 존재 체크로 시작해도 충분하다.

```

입력된 회사 정보와 업무 현황만 근거로 분석하고, 반드시 주어진 JSON 스키마 형식으로만 응답하세요.
스키마에 없는 필드를 추가하거나 설명 텍스트를 덧붙이지 마세요.
모든 수치(절감 시간 등)는 입력값에 기반한 추정치이며, 보장된 값처럼 과장하지 마세요.
우선 추천 업무는 3~5개로 제한하고, 실행 난이도가 낮은 것부터 우선순위를 매기세요.
```

### 7.3 Structured Output 스키마 (OpenAI `response_format`)

```json
{
  "name": "diagnosis_result",
  "strict": true,
  "schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["automationScore", "priorityTasks", "totalEstimatedSavedHours", "recommendedStack", "implementationSteps", "summary"],
    "properties": {
      "automationScore": { "type": "integer", "minimum": 0, "maximum": 100 },
      "priorityTasks": {
        "type": "array",
        "minItems": 3,
        "maxItems": 5,
        "items": {
          "type": "object",
          "additionalProperties": false,
          "required": ["name", "reason", "difficulty", "estimatedMonthlySavedHours"],
          "properties": {
            "name": { "type": "string" },
            "reason": { "type": "string" },
            "difficulty": { "type": "string", "enum": ["낮음", "중간", "높음"] },
            "estimatedMonthlySavedHours": { "type": "integer" }
          }
        }
      },
      "totalEstimatedSavedHours": {
        "type": "object",
        "additionalProperties": false,
        "required": ["min", "max"],
        "properties": { "min": { "type": "integer" }, "max": { "type": "integer" } }
      },
      "recommendedStack": { "type": "array", "items": { "type": "string" } },
      "implementationSteps": { "type": "array", "items": { "type": "string" } },
      "summary": { "type": "string" }
    }
  }
}
```

Gemini를 쓸 경우 동일한 구조를 `responseSchema` 옵션에 그대로 옮기면 된다(필드명·타입 동일, `additionalProperties`/`strict` 키만 Gemini 문법에 맞게 제거).

```yaml
      - npm_data:/data
```
